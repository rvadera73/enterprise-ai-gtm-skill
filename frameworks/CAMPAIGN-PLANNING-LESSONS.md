# Campaign Planning Lessons

What a long, iterative campaign-planning session (2026-08-14, the AI Forge/
AI-Assisted Software Engineering GTM effort) surfaced. Written as durable rules with
the evidence attached — same spirit as `content/video/GTM-ASSET-PLAYBOOK.md` §4, but
for campaign/journey-mapping decisions rather than a single asset's production.

## 1. Check the user's own real, prior precedent before researching theory or inventing a framework

The single biggest time sink this session: building an invented campaign structure
("Anchor-and-Orbit," numbered "waves") from first principles, having it correctly
rejected as not landing, then running four external research passes (generic
content-marketing models, solo tech bloggers, GovCon primes, LinkedIn-native
creators) before finally being pointed at the user's own already-published,
already-successful campaign (the RiskModelForgeIQ launch: a numbered LinkedIn post
series, each tied to a specific video, cross-linking back to the prior post, BLUF-
first and short, teasing not narrating) as the actual template to replicate.

**That real precedent should have been the FIRST thing checked**, not the last —
before inventing new terminology, before external research. If the user has already
run a comparable campaign for a related product, that real, observed-working pattern
outranks any theoretical model, however well-sourced.

**How to apply:** before designing any new campaign/content structure, ask
explicitly: has this person (or this org) already done something like this? Look at
their real prior published work first.

## 2. The pattern that actually got agreed on, once grounded in real precedent

Pick a real pain point (framed at the capability level — see
`positioning/AUTHENTIC-MESSAGING-PROFILE.md` for voice, and never naming a specific
government pursuit — see `gtm-govcon-linkedin-not-validated-channel` in the author's
memory for why) → write ONE substantive piece (blog post or white paper) in
individual voice, real experience as proof, not corporate press-release voice →
pull several LinkedIn posts from that piece over the following weeks → repeat for
the next pain point/differentiator. The unit of planning is one pain point at a
time, not a pre-fixed campaign calendar — this is what makes the structure survive
scope evolving (new differentiators/products surfacing mid-campaign) without
needing to be re-planned from scratch.

## 3. Verify claims at the MECHANISM level, not just the fact level

Rule 0 (`VIDEO-ASSET-TEMPLATES.md`) already requires web-verifying every cited
figure. This session surfaced a second, subtler failure mode: a claim can be
*directionally* true while overclaiming **who or what** actually does it. Real
example: "AI agents generate continuous ATO compliance evidence" sounds like one
claim, but it's actually two different claims bundled together — "automated
pipelines generate continuous compliance evidence" (real, proven since 2018 via
DoD's Platform One/Kessel Run) and "AI agents specifically, at runtime, generate
that evidence" (not documented anywhere as of this session's research — a genuinely
novel claim). Always ask: is the AGENT of this claim (a human-written deterministic
pipeline vs. an AI agent acting autonomously) actually what's being described, or is
a more impressive-sounding mechanism being assumed because the surrounding narrative
involves AI elsewhere?

## 4. Rule 0, a real catch from this session

Two of four headline industry-benchmark stats on an internal positioning deck did
not survive verification: a "75% faster PR turnaround (9.6→2.4 days)" claim turned
out to be an internally-inconsistent conflation of a real but different case-study
number (GitHub/Duolingo's actual published figure is "67% decrease in review
turnaround," no day-counts anywhere); a "$150B federal AI spending by 2027" figure
had no findable source at all (the real Deltek forecasts are either $2.1B→$3.1B
AI-specific or $116.4B→$137.5B for broader federal IT, neither close to $150B). Both
had been sitting on a real internal slide, unchallenged, presumably because they
"sounded right." Web-verify every number before it reaches a draft, including
numbers that already exist on an internal source document — internal materials are
not pre-verified just because they're internal.

## 5. When positioning language evolves, flag which version is current

This session found two DIFFERENT architectural taxonomies for the same overall
"Enterprise AI Foundry" brand: an older one (`examples/whitepapers/
ENTERPRISE-AI-FOUNDRY-STRATEGIC-WHITEPAPER.md`: Agentic Engineering Factory + Agile
Software Fabric + AI Services Infrastructure) and a newer one (a July 2026 internal
deck: Agile → AI-DLC → AI-Assisted Software Factory, five governed workflows). Both
are real, but only one is current — the newer deck supersedes the older whitepaper's
framing. Neither file says so. **When a product's positioning terminology evolves,
the newer source doesn't automatically flag the older one as stale** — check the
most recent real source (an actual current internal document, not an example/draft
folder) before assuming a `examples/` or `archive/` file reflects current thinking.
